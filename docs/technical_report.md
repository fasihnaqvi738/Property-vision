# Property Vision technical report

**Engineering snapshot:** 2026-10-03  
**Status:** engineering implementation report; acceptance accuracy gates are not yet passed.
**Length:** intentionally kept within the six-page limit when rendered as a normal technical memo.

## 1. System and capture route

Property Vision accepts room-photo folders, video files or room-video collections, the supplied RGB-D bundle, an extracted Polycam Raw Data folder, and an extracted ARKitScenes raw RGB-D scan folder. Photo/video features are reconstructed with CPU `pycolmap`/COLMAP; run-to-run reconstruction can vary even with identical inputs, so the saved model and registered-image counts must be treated as per-run diagnostics. Video is sampled with OpenCV before sparse reconstruction. RGB-D/LiDAR frames are back-projected using depth, intrinsics, and supplied poses; review-only floor and wall analyses produce point clouds and geometric hypotheses. Every new capture writes a timestamped result under `outputs/`, checks it against `schemas/property_capture_result.schema.json`, and preserves the source capture path. The ARKitScenes adapter now runs on both a synthetic layout fixture and public raw scan `42445884`; its sparse trajectory is joined to sensor streams by nearest timestamp. The real sample was captured on iPad Pro, not iPhone; an iPhone sample is unavailable [Lack of access to an iphone].

The selected user route is the stock-capture protocol in `docs/capture_protocol.md`: iPhone Camera for photos and video, plus Polycam Space/LiDAR Raw Data on a Pro-class iPhone for depth. The protocol asks the operator to choose Camera → Formats → Most Compatible so photos hand off as JPEG and video as H.264, reducing codec ambiguity on Windows; HEIC/HEIF stills are also decoded and converted to run-local JPEG staging files. The project does not ship an iOS app. Device identity and iOS/app versions are unknown for the data presently tested [Lack of access to an iphone]. Install `requirements.txt` before the visit so the HEIF codec is present.

## 2. Output and evidence

The shared JSON schema is enforced on serialization. It carries per-room geometry slots, stitched-plan slots, damage/scope sidecars, artifact paths, calibration status, drift status, and limitations. Unsupported measurements stay unavailable. A valid schema proves data shape, not geometric correctness or that a room has been reconstructed successfully. The rendered floor plan available today is a human-traced reference from the supplied plan image, not a plan inferred from the scans.

The strongest current RGB-D run, freshly replayed from `captures/c00a170fe1` with the pinned dependencies on Python 3.12.14, sampled 172 of 1,715 frames and exported 528,384 colored points in 20.029 seconds. A fresh 2026-10-03 run with scan stitching at `outputs/feature_lidar_final/c00a170fe1_20261003T123336405747Z/` sampled the same input, took 14.547 seconds, and emitted one four-sided 3.3041 m² candidate plus floor, wall, and geometry-review artifacts. The pipeline detects pairwise overlaps, excludes conflicts from the footprint sum, records shared-edge adjacency hypotheses, and writes `scan_stitched_plan.geojson` and `.svg` with the capture-local metric coordinate system identified. The supplied scan has one candidate, zero adjacency pairs, and zero overlaps, so it does not demonstrate multi-room stitching. A synthetic geometry check confirmed that adjacent candidates link and an overlapping candidate is excluded from the footprint sum. The new result passed the shared schema. Dimensions have no independent measurement or calibrated interval; the candidate is not an accepted room.

Visible damage classification is integrated through Roboflow's hosted `wall-damage-detection/1` detector for cracks, flaking paint, missing material, and water damage. `pipeline/damage_inference.py` converts prediction boxes into evidence polygons and preliminary scope line items. Crack takeoff is a box long-axis; other classes use box area. Quantities stay in pixel units unless the operator supplies an approximate planar image scale; even then they remain partial because box masks and perspective correction are absent. Inference sends the input images to the hosted API and requires `ROBOFLOW_API_KEY`; the public model page reports 0.48 mAP@50, 0.644 precision, and 0.473 recall. No apartment damage images have been evaluated against independent ground truth, and no concealed-damage or price/material estimator is implemented.

To exercise the real ARKitScenes adapter, one public raw scan (`42445884`, visit `422009`) was downloaded locally with its source URLs and asset SHA-256 hashes recorded. A fresh RGB-D replay exported 78,343 points in 3.281 seconds and passed schema validation. A separate evaluator paired 40 unique low-resolution sensor-depth frames with dataset high-resolution depth projected from a FARO-derived mesh: 350,043 valid pixels, 0.0218 m MAE, 0.015 m median absolute error, 0.041 m P90, with 93.293% within 5 cm. The image/pose/reference pairing and raster resize are assumptions; this is useful LiDAR depth evidence but not an iPhone evaluation [Lack of access to an iphone], room-dimension, floor-plan, or calibrated-interval pass. Full details are in `docs/benchmark_report.md` and the ignored local report `outputs/case_statement_replay/arkitscenes_depth_evaluation.json`.

The latest apartment photo replay registered 7/23 stills in independent room models (3/3 third-bedroom, 4/4 living/dining) and 20/23 in its largest joint COLMAP model spanning all eight labels; runtime was 123.443 seconds on Python 3.12.14 with the pinned dependencies. The largest model has 348 sparse points and is still arbitrary scale. The joint pass fixes COLMAP's random seed and uses one CPU thread. Two earlier joint-only repeats on the same staged inputs registered the exact same 20 image names. The fix-loop package at `benchmark/photo_registration_fix/` records a diagnostic comparison of 8/23 before to 20/23 after; the actual whole-property stitch remains unscored. This addresses run-to-run model membership on this input, but not cross-device robustness: the joint camera poses are not verified room placement, adjacency, or a floor plan. The one-thread exhaustive matcher is slower; this run remains under the 900-second local limit. A separate HEIC route run converted five generated HEIC derivatives of the ISPRS stills; all five registered and schema validation passed in 20.247 seconds. This confirms file-format handling, not native iPhone capture behavior [Lack of access to an iphone]. The edited 214-second promotional walkthrough was split into 11 human-reviewed intervals; 7/11 intervals made a sparse model and 4/11 had a model with at least three registered frames. Its run took 472.56 seconds. A fresh 37.2-second RGB-D sample video run sampled 143 frames and produced six disconnected models in 85.268 seconds (largest: 23 frames, 16.1%). These are sample/listing materials, not independent iPhone walk-in evidence [Lack of access to an iphone]. `docs/benchmark_report.md` records the gate-by-gate evidence and regeneration commands.

## 3. Layout, drift, and uncertainty

Room subfolder labels are carried through the photo result, but independent SfM coordinate frames do not place those rooms relative to one another. The joint photo model reports visual model connectivity only; it does not infer doors, adjacency, footprint, metric scale, or overlaps. The new scan-derived candidate stitch operates only on polygons already projected into one supplied RGB-D world frame; it does not place separately captured or photo-derived room models. The manual reference plan has 8 primary rooms/lobby, 5 ancillary spaces, 2 connectors, and 14 annotated adjacency records; these are traced in drawing pixels and are not scan predictions or an independently surveyed footprint. The user's printed room dimensions remain authoritative per-room targets, but a reproducible scale audit of 11 traced room polygons found a 27.6% RMS residual even after fitting independent X/Y pixel scales and choosing each room's better dimension orientation. The image trace therefore cannot be made into a metric stitched plan with a single global transform; the audit is kept at `outputs/apartment_case_01/stitched_plan/plan_scale_audit.json`.

The Polycam adapter can select raw or corrected camera poses and an evaluator can compare runs from the same export. No actual Polycam capture [Lack of access to an iphone] or ground-truthed raw/corrected ablation is available. The supplied RGB-D path uses its pose stream as provided. Consequently, this implementation does **not** demonstrate accumulated-drift correction on a multi-room capture.

The Apartment plan supplies 11 complete printed room-dimension pairs plus one partial pair, which are treated as authoritative scoring targets for this property per user instruction. No phone-sensor predictions are paired to those targets [Lack of access to an iphone], and no independent tape/laser cross-check exists. One external depth-raster comparison now exists, but there is still no calibration set pairing Property Vision's room measurements and confidence intervals with surveyed room truth. RGB-D boundary lengths/areas remain provisional under pose/axis assumptions; photo/video SfM has arbitrary scale. The plan has no ceiling-height or opening-width truth and does not provide the unseen walk-in property's measurements; the accuracy, repeatability, and footprint gates remain unscored.

## 4. Gates and fix loop

No case-study accuracy gate is scored. The repository contains benchmark templates and an evaluator for openings, ceilings, repeated walls, footprints/adjacency, runtime, and a same-room incumbent comparison. The required measured manifest is not present. In particular, the current assets do not provide three rooms plus connector captured in all three tiers [Lack of access to an iphone], staged damage in two classes, a same-tier repeat, laser/tape readings, or a Polycam/consumer-app comparison export.

A concrete input-path defect was found during the cold-run audit: HEIC was recognized by capture detection but excluded by photo enumeration, while capture loading eagerly decoded all full-resolution photos. The path now accepts HEIC/HEIF, validates/decode-stages images for COLMAP, and avoids retaining all 48 MP images at initial load. A generated HEIC smoke input decoded and staged successfully. This is an engineering reliability repair, **not** a fix-loop accuracy result: no measured failing accuracy gate or honest before/after metric exists yet. The declaration template must not be filled with a fabricated gate.

## 5. Walk-in risks and reproduction

The likely failure modes on a new property remain low texture, blur, motion, repeated patterns, poor doorway overlap, mirrors/glass, reflective or wet surfaces, low light, occlusion, and edited/variable-frame-rate video. Polycam export folder/version differences, iPhone codec differences, and corrected-pose conventions still require a real-device check. Photo/video/RGB-D reconstruction runs locally after capture and do not require a hosted service. The optional Roboflow damage workflow is different: it sends selected images to Roboflow and requires a private API key. The assessment's cold iPhone run cannot be certified without an actual iPhone 15+ capture [Lack of access to an iphone] and exported Pro LiDAR data.

From the repository root, install pinned dependencies, then run one of the README commands on the raw capture. Add `--device "model | OS version | app version"` to preserve the actual hardware/software identity. Validate a generated result with `python -m pipeline.validation outputs\\<run>\\result.json`. For the supplied RGB-D sample, the captured command was `python main.py captures\\c00a170fe1 --output-dir outputs`; the report and JSON result retain its runtime and artifact paths. Keep raw captures and generated visual files local/ignored; submit code, manifests, schemas, and report text without committing private or large capture imagery.

**Assessment:** reproducible capture routes and a shared output contract are in place; the central product claim (a metric, damage-aware, stitched plan from any of the three tiers) and measured assessment gates remain unproven. Describe the current result as an engineering implementation with diagnostic outputs, not as a passing accuracy submission.
